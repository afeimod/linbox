# LinBox 内置 X11 桌面（v2.22.2）

LinBox 现在自带 X11 显示端：在终端里一条命令即可把图形化 Linux 桌面
（xfce4 / openbox 等）投射为 **LinBox 桌面内的一个窗口**（fix9.6 起）
——窗口可自由拖拽/缩放/最大化/一键真全屏，分辨率可跟随窗口或固定；
不嵌入终端界面，也不抢占整屏。实现方法参考
[jiaxinchen-max/termux-app](https://github.com/jiaxinchen-max/termux-app)
的内置 X11 方案（基于 termux-x11 上游：lorie 合成器 + Xwayland 内嵌库），
并按 LinBox 的包名/前缀/桌面形态做了适配。

## 一、工作原理

```
LinBox 终端                        LinBox App 进程
────────────                       ─────────────────────────────
$ linbox-x11 :13
  └─ termux-x11 脚本
       CLASSPATH=宿主 APK
       app_process →
         CmdEntryPoint.main()
           native start():
             lorie + Xwayland
             （X server 运行在
              终端侧子进程）
           每秒广播 ACTION_START
           （binder 携带连接 fd）──→  LinBoxApp 动态接收器
                                        └─ 拉起全屏 X11 桌面
                                           Activity（不进终端界面）
                                           └─ 从重播取 binder →
                                              getXConnection(fd) →
                                              LorieView 渲染
$ env DISPLAY=:13 startxfce4   ──→   X 屏幕尺寸 = 视图尺寸（自动调节）
```

- **X server 端**：`libXlorie.so`（四 ABI 预编译）随 APK 分发，由
  `app_process` 在终端侧子进程加载运行，X11 socket 落在 LinBox 自身
  的 `usr/tmp`，终端里的 X 程序直接 `DISPLAY=:13` 连接，无需任何代理。
- **显示端**（fix9.6）：`X11Surface` 把 `LorieView`（SurfaceView）
  嵌入 LinBox 桌面窗口（`X11WindowController` 完成广播→开窗→取
  fd→连接），画面随窗口自由拖拽/缩放/全屏；独立全屏 Activity
  （`com.termux.x11.MainActivity`）保留作兼容兜底入口。
- **输入**：直触模式（触摸点按 视图→X 屏幕比例直注）+ 软键盘开关
  （窗口控制条）；外接键鼠/手柄映射/扩展按键条沿用上游能力。
- **分辨率自适应**：`displayResolutionMode` 默认 `native`，X 屏幕尺寸
  实时跟随视图尺寸（旋转/全屏切换即时调整 X11 RANDR）；窗口控制条
  可随时切换为固定分辨率（如 1280x720）。

## 二、与 X11 应用不冲突

| 维度 | LinBox 内置 | 官方 Termux:X11 应用 |
|------|------------|---------------------|
| 宿主包名 | com.linbox | com.termux |
| 广播目标 | `TERMUX_X11_OVERRIDE_PACKAGE=com.linbox` | com.termux |
| X11 socket | com.linbox 的 tmp | com.termux 的 tmp |
| 进程名 | `linboxx11` | `com.termux.x11` |
| 显示号 | 默认 `:1`（可用 `:0`/`:2`…） | 任意 |

两者可同时安装、同时运行，互不干扰。

## 三、使用

```sh
# 0. 体检（可选，查看组件/依赖是否就绪，缺什么给什么命令）
linbox-x11 doctor

# 1. 安装桌面环境（首次；只有这一步需要 pkg，X 服务本体无需装任何包）
pkg update && pkg install x11-repo && pkg install xfce4 dbus

# 2. 启动（LinBox 桌面自动弹出 X11 窗口并拉起 xfce4）
linbox-x11

# 或指定显示号 / 只跑单个程序
linbox-x11 :13
linbox-x11 :13 xterm

# 手动启动会话请带 dbus-launch（无会话总线桌面会黑屏）
env DISPLAY=:13 dbus-launch startxfce4

# 3. 停止
linbox-x11-stop
```

也可以从 LinBox 桌面「开始菜单 → X11 桌面」直接打开窗口等待连接；
窗口控制条可切换分辨率（跟随窗口/固定）、唤起软键盘、一键真全屏
（返回键退出全屏）。

## 四、依赖说明（澄清常见误解）

**X 服务本体不依赖任何 pkg 包。** `CmdEntryPoint + libXlorie.so`
内置于 LinBox APK；XKB 键盘数据（源自 xkeyboard-config 2.48）fix9.10
起随 bootstrap 归档分发（归档内 `xkb/x11-xkb.tar.gz` 成员，三级容错
部署），首次启动自动解压，开箱即用；`termux-x11-nightly`
不是必需依赖（装不装都不影响内置 X11——装了也会被 debfix/linbox-x11
自动换回内置客户端，防止官方脚本经前缀重写后类名不存在导致的启动崩溃）。

需要通过 pkg 安装的只有「显示什么」：

| 组件 | 作用 | 安装命令 |
|------|------|---------|
| xfce4 + dbus | 完整桌面（推荐） | `pkg install x11-repo && pkg install xfce4 dbus` |
| openbox | 轻量窗口管理器 | `pkg install x11-repo && pkg install openbox` |
| xterm | 最小化验证 | `pkg install x11-repo && pkg install xterm` |

什么都没装时服务照常启动，只是没有可显示的窗口——终端会提示安装命令。
用 `linbox-x11 doctor` 可随时查看缺什么。

## 五、排障（linbox-x11 启动失败时）

启动全程写入 `$PREFIX/tmp/linbox-x11.log`（前置检查、自愈动作、
X 服务输出一站齐全）：

```sh
cat $PREFIX/tmp/linbox-x11.log   # 完整日志
tail -20 $PREFIX/tmp/linbox-x11.log
```

- 日志不会再出现“完全空白”：脚本第一行即写入启动横幅；X 服务在
  native 层静默失败（原因仅写 logcat）时，`linbox-x11` 会自动附带
  logcat 相关摘要。
- `linbox-x11 doctor`：逐项检查客户端/主副本/宿主 APK/
  libXlorie.so/app_process/XDG_RUNTIME_DIR 与桌面依赖，结论区直接给
  处理命令。
- 显示号 socket 被残留占用：先 `linbox-x11-stop` 再启动。
- `bin/termux-x11` 被官方包覆盖：启动时自动从 `etc/linbox/x11` 主副本
  恢复（日志中会记录恢复动作）。
- **libXlorie.so 加载失败**（logcat 见
  `dlopen failed: ...base.apk!/lib/...` 或 `UnsatisfiedLinkError`）：
  LinBox 以 useLegacyPackaging=true 打包，APK 内 lib 条目被压缩无法
  直接 dlopen，X 服务优先从 PM 解压目录（nativeLibraryDir）加载；
  若仍失败，`linbox-x11` 前置检查会直接提示 ABI 不匹配/安装不完整
  （建议安装 universal 包）。
- **Bootstrap 安装失败 / termux/x11-xkb.tar.gz**（fresh 安装首次启动
  终端全屏报错，9.7~9.9 实锤）：独立 XKB 资产在 CI 仓库管线中整文件
  丢失（*.tar.gz 在 git 提交/检出环节被吞，而 bootstrap *.zip 从未
  丢过），安装收尾对它的单点拷贝抛 FileNotFoundException → 整个
  bootstrap 安装被判失败 + revision 永不落盘（每次启动迁移重跑再
  失败）。fix9.10 根治：XKB 数据改随 bootstrap 归档分发
  （`xkb/x11-xkb.tar.gz` 成员，SHA 同步）+ 三级容错部署
  （bootstrap 内 → 独立资产 → 存量保留），任何来源缺失仅告警
  不阻断安装。已刷坏的设备：装 fix9.10+ APK 打开一次主界面即自动
  完成迁移与救援库部署。
- **XKB_CONFIG_ROOT is not set**（日志可见，X 服务随即
  System.exit(1)）：XKB 键盘数据缺失。fix9.10 起数据随 bootstrap
  归档分发（三级容错部署为 etc/linbox/x11/xkb.tar.gz，首次启动
  自动解压为 xkb/ 并导出 XKB_CONFIG_ROOT）；若仍提示缺失，打开一次
  LinBox 主界面重新部署，或 `pkg install xkeyboard-config`。
- **CANNOT LINK EXECUTABLE "…/dbus-daemon": library "libexpat.so.1"
  not found**（dbus-launch 尾随 "EOF in dbus-launch reading address
  from bus daemon"）：会话组件的 pkg 动态库缺失/损坏。fix9.9 排查
  实锤两个根因：① bootstrap 原包把 libexpat.so / libgpg-error.so
  以 dev 名入库且 SYMLINKS.txt 无 soname 条目 → libexpat.so.1 从
  不存在，而 dpkg status 已登记 installed → 依赖方永远不会再解包；
  ② 历史 dpkg 事故还可能整文件丢 liblz4.so.1（apt → libapt-pkg.so
  的依赖）→ pkg/apt 自身也 CANNOT LINK，连 pkg install 都无法自救。
  修复（rev20）：直接运行 `linbox-pkgfix`（离线补 soname 链接 +
  救援库三级兑底 + 逐二进制实跑验证，不依赖 pkg/网络/主界面，
  幂等）：优先用主界面部署的 etc/linbox/rescue 副本；副本也缺时
  v1.1 起直接从宿主 APK 内嵌 bootstrap 归档提取真身（ELF 魔数
  校验，历版 APK 均适用）；或 `linbox-x11`（会话预检失败时自动
  先跑一遍）；pkg 恢复后执行
  `pkg reinstall liblz4 libexpat libgpg-error && pkg upgrade` 把
  dpkg 数据库摆正防复发，再重跑 `linbox-x11 :13`。新装环境
  （bootstrap rev20 归档 + SHA 同步更新）不再含此缺陷。
- **窗口/画面已出但触摸无反应**（fix9.6 已修复）：旧版显示端把触摸
  事件整条吞掉未转发 X server（显示动不了/叉叉划不动）；升级到
  fix9.6 即恢复正常。
- **X11 窗口黑屏/画面空白**：多为桌面会话未起来——手动
  `startxfce4` 未带 dbus-launch 时无会话总线，xfwm/xfdesktop 起不来，
  根窗口呈黑色。请用 `env DISPLAY=:13 dbus-launch startxfce4` 或
  直接 `linbox-x11`（自动带 dbus-launch）；也可先 `linbox-x11 :13 xterm`
  验证 X 服务与显示链路本身是否正常。
- **连接状态**：X11 窗口未连接时会显示等待页与指引；若等待页长时间
  停在“正在连接”，运行 `linbox-x11 doctor` 并检查
  `$PREFIX/tmp/linbox-x11.log`。

## 八、v2.22.3 fix10：分辨率握手 · z 盘 · 虚拟手柄 · 鼠标点击（本次修复）

### 8.1 X 屏幕分辨率真正跟随 `glibc-runner -d`

终端 → 窗口的**分辨率握手协议**（文件 `$PREFIX/tmp/.linbox-x11-res`）：

| 终端命令 | 写入内容 | X11 窗口行为 |
|----------|----------|--------------|
| `glibc-runner -d1280x720 game.exe` | `1280x720` | X 屏幕建为 1280x720，画面等比缩放进窗口（信箱居中） |
| `glibc-runner -d game.exe`（全屏） | `1280x720` | 同上（全屏默认桌面分辨率） |
| `glibc-runner game.exe`（窗口模式） | `native` | 跟随窗口（旧行为） |
| `linbox-x11`（桌面会话） | `native` | 跟随窗口（复位，避免游戏分辨率粘住桌面） |

实现：`X11ResolutionLink`（FileObserver 监听）→ 写 X11 偏好
（`displayResolutionMode=exact/native`）→ `LorieView.regenerate()` →
native `sendWindowChange` → X server RandR 调整屏幕尺寸。DXVK/游戏
从此按真实分辨率渲染（修复"游戏缩在左上角一小块"）。
控制条实时显示当前 X 分辨率（来自 glibc-runner 时高亮）。

### 8.2 wine z 盘永不为空（glibc-runner v3.2-linbox3）

- `glr_ensure_std_drives` 改用 `[ -e ]`（跟随链接）判定 —— **悬空盘符
  自动删除重建**（旧逻辑把悬空链接当"已存在"，z: 一旦失效永不修复）；
- `z:` 统一指向 `/`（wine 标准），根文件系统恒非空，天然覆盖 app 私有
  目录与 /sdcard；
- `--install-prefix` 与每次启动静默补齐路径同步修复；z: 创建不再依赖
  drive_c 存在。

### 8.3 虚拟手柄作用于 X11 界面

- 新增 `X11InputHub`（进程级单例）：WinHandler（UDP 7947，wine 侧
  winhandler.exe 对端）浮动窗口/全屏 Activity **共享单实例**，幂等启动；
- X11 桌面窗口叠加 Winlator 手柄层（`InputControlsView` + 触控板回落），
  控制条**"手柄"按钮一键开关**（profile 自动记忆/恢复）；
- `MainActivity.dispatchTouchEvent` 补上手柄触摸路由（原 fork 缺失，
  全屏模式点按钮也无反应）；
- 多指同时按住时松开一指不再误释放其它指（粘键/串键修复）。

### 8.4 触摸 → 真鼠标（SmartTouchBridge）

直注原生 X 触摸事件在 wine 下点不开文件/文件夹，且双击、落点都不可靠。
新的智能鼠标桥：

| 手势 | 动作 |
|------|------|
| 单指轻点 | 左键单击（按下即移动到指尖，落点零偏移） |
| 两次轻点 | **双击** —— 第二击自动吸附到第一击的 X 坐标（±450ms），wine 稳定识别 WM_LBUTTONDBLCLK，双击打开文件/夹 |
| 单指按住拖动 | 左键按住拖拽（移动 wine 窗口/滚动条） |
| 双指轻点 | 右键单击 |
| 双指滑动 | 滚轮 |

坐标变换：`视图像素 × (X屏幕/视图尺寸)`，固定分辨率模式下信箱等比、
无偏移。

### 8.5 部署说明

- 增强版 `glibc-runner`（v3.2-linbox3）已入库 `assets/termux/scripts/`；
  `TermuxBootstrapInstaller`（rev 22）部署主副本到 `etc/linbox/glibc-runner`
  并在缺失时落位 `bin/glibc-runner`；`linbox-glibc` 安装 glibc-runner 包后
  自动恢复增强版（防 pkg 覆盖）。
- 存量设备手工更新：把 `glibc-runner` 覆盖到
  `/data/data/com.linbox/files/usr/bin/glibc-runner` 并
  `chmod 700` 即可。

## 九、v2.22.6 fix18/fix19：自适应铺满 · wine 虚拟桌面选项

### 9.1 铺满策略（X11FitClient）

窗口化游戏（DirectDraw 固定分辨率老游戏、未全屏的现代游戏）自动铺满，
不再需要手动把分辨率改成和游戏一致：

| 策略 | 机制 | 适用 |
|------|------|------|
| **贴合拉伸**（默认） | 平移游戏客户区到 (0,0) + X 屏幕缩成游戏客户区尺寸 + 显示层拉伸铺满 | 任意窗口化游戏（含老游戏），可靠无黑边 |
| **撑满**（`-F/--fitwin`） | 把游戏窗口 resize 到整个 X 屏幕，游戏按 -d 分辨率原生渲染 | 能跟随 WM_SIZE 重绘的现代游戏（比拉伸清晰） |
| 稳定态零动作 | 窗口已对齐且 == X 屏幕（真全屏/虚拟桌面） | 不与游戏抢权 |

fix19 反转了 fix18 的默认策略：撑满把窗口 resize 成功后，老游戏仍在
原分辨率区域绘制（如 868x652），X 层"窗口==屏幕"假稳定 → 右/下黑区。
贴合把"分辨率==游戏分辨率才撑满"这个用户验证过的静态场景自动化了。

### 9.2 wine 虚拟桌面（`-v/--vd`，轩辕剑4 类必开）

部分游戏（轩辕剑4 等）离开 `explorer /desktop` 虚拟桌面会报错/黑屏，
必须运行在虚拟桌面内：

```bash
glibc-runner -v1024x768 game.exe          # VD 1024x768
glibc-runner -d1024x768 -v game.exe       # 等价（-d 指定尺寸 + -v 开 VD）
glibc-runner -v game.exe                  # VD 默认 1280x720
GLR_VD=1 glibc-runner -d1280x720 game.exe # 环境变量等价物
```

VD 尺寸与握手分辨率一致 → VD 窗口恰好铺满 X 屏幕，无黑边。
`-F/--fitwin` 把握手值标记为 `WxH fitwin`（App 侧走撑满策略，

## 十、v2.22.7 fix20：Wine 声音管线修复

### 10.1 根因（三层断裂）

用户实测的三个报错对应声音链路的三处断裂：

| 报错 | 根因 |
|------|------|
| `pulseaudio: /proc/self/exe does not point to ... cannot self execute` | 服务端在 `/data/user/0/` 绑定路径下启动，pulse 自检（编译期路径必须与 /proc/self/exe 一致）失败拒启 |

完整链路（自动，无需手工干预）：


- **[A1] 服务端**：glibc-runner 在 bionic 隔离子壳里启动 pulseaudio

- **[A2] 客户端库**：首启自动 `pkg install libpulse-glibc alsa-lib-glibc

- **[A3] PULSE_SERVER=127.0.0.1** 注入 wine 环境；启动横幅显示

- **[A5] 注册表自愈**：Drivers 被钉死 alsa 时自动改写 `pulse,alsa`

- **[A6] bionic 工具安全化**：脚本自身在 glibc 环境下调用的

## 十一、v2.22.8 fix21：声音偏小（"被压住"）音量归一化

### 11.1 根因

声音链路修通（fix20）后仍可能出现"声音能出但明显偏小，像被什么压住"。
这不是单一故障，而是音量叠加链上多层的默认值偏保守：

| 层 | 问题 |
|----|------|
| pulse sink | Android 上 sles 输出 sink 的默认音量可能低于 100% |
| flat-volumes | wine 流注册音量较低时会把 sink 总音量一起拉低 |
| 静音残留 | 上次会话的 sink 静音状态未清除 |
| Android 媒体音量 | 与 App 音量独立，需在播放中按音量键确认 |

另有一个 fix20 遗留 bug 藏在其中：`glr_port_up` 端口探测成功后执行的
`exec 3>&- 3<&- 2>/dev/null` 把整个脚本的 stderr 永久吞进 /dev/null ——
端口就绪后所有警告（含音量设置失败提示）静默丢失，`bash -x` 调试也
会断流。fix21 已删除该行（探测 fd 在子壳内自动关闭，本就无需关闭）。

### 11.2 修复（glibc-runner v3.8-linbox1）

- **[V1] 音量归一化**：pulse 服务端就绪后自动 `pactl` 解除静音 +
  `set-sink-volume @DEFAULT_SINK@` 归一到 100%（环境变量
  `GLR_AUDIO_VOLUME=50~300` 可调，>100 为软件增益，过大会削顶/放大
  底噪，逐档试听）。sink 刚拉起未就绪时重试 3 次。
- **[V2] --fix-audio 诊断增强**：输出 sink 名称/状态/静音/音量、
  活动音频流（sink-inputs）与增益提示；pactl 统一走 bionic 隔离子壳
  （`PULSE_SERVER=127.0.0.1`）。
- **[V3] 启动横幅**：audio 行显示生效音量（如 `· sink音量 100%`）。
- **[V5] stderr 吞没修复**：见上，端口探测不再永久重定向 stderr。

### 11.3 使用与排障

```bash
glibc-runner -d1024x768 game.exe            # 默认归一 100%
GLR_AUDIO_VOLUME=150 glibc-runner game.exe  # 偏小 → 软件增益 1.5 倍
glibc-runner --fix-audio                     # 看 sink 状态/静音/音量诊断
```

| 症状 | 处置 |
|------|------|
| 声音偏小 | 先确认 Android 媒体音量(播放中按音量+)与游戏内音量；再 `GLR_AUDIO_VOLUME=150` 逐档上调(150→200→250) |
| 横幅显示 `· sink音量 N%` 仍小 | `--fix-audio` 看 sink 状态块：State 应为 RUNNING、Mute 应为 no |
| `--fix-audio` 显示有活动流但流音量低 | 游戏内音量设置或该流被流恢复表记住低音量：游戏内调满后重启游戏 |
| 音量警告 "音量设置未生效" | pactl 缺失或 sink 未就绪：`pkg install pulseaudio` 后重试 |
| 增益后出现破音/底噪 | 增益过大削顶，回调 `GLR_AUDIO_VOLUME`（100~150 区间为宜） |

## 十二、v2.22.9 fix22：前缀构建修复 · Z 盘新指向 · zink 渲染

### 12.1 根因：无 .wine 前缀时 wineboot "假成功"

用户实测：首次启动（无 `.wine` 前缀）时前缀无法正常构建，每次启动都刷

```
wine: could not open working directory L"C:\windows\system32\", starting in the Windows directory.
```

这不是 wine 本身的 bug，而是 LinBox 增强脚本与 wine 前缀创建机制的一次精确碰撞：

| 环节 | 事实 |
|------|------|
| wine 前缀创建 | wine（server 端）**只在"自己亲手创建 `dosdevices/`"时**才会顺带创建 `drive_c/` 与 `c:`/`z:` 链接（`server.c`：`mkdir(dosdevices)` 成功 → 建 drive_c；已存在 → 整段跳过） |
| 旧版 glibc-runner | `[W11]/[Z1]` 的"每次启动自动补盘符"在 `glr_env_core` 里就 `mkdir -p $WINEPREFIX/dosdevices` 并链接了 `z:` —— **早于 wineboot** |
| 结果 | wineboot 面对"已存在的空壳 dosdevices"：`drive_c`/`c:` 永不创建 → C: 盘缺失 → 前缀报废，每个 wine 进程启动都报上面的 working directory 错误 |
| 旧判据帮凶 | 自动初始化的"成功"检查只查 `system.reg`（server 侧文件，能写出来）→ 半成品前缀被误判为"创建成功" |

startonwine（Mobox 参考实现）从不预创建 dosdevices：先 `rm -rf $WINEPREFIX`，
干净环境下 `wineboot -u`，再用 `.update-timestamp` 验收，最后才补盘符。

### 12.2 修复（glibc-runner v3.9-linbox1）

- **[B1] 前缀自动构建重构（startonwine 语义）**：
  - `glr_ensure_std_drives` 在前缀未初始化（无 `system.reg`）时**整体跳过**，
    绝不预创建 dosdevices；
  - 新增 `glr_bootstrap_prefix`：旧/半成品/损坏前缀先备份挪走 → 干净环境下
    `wineboot -u`（关闭 box64 dynarec 干扰项与 esync、屏蔽
    mono/gecko/winegstreamer） → **三重验收**（`system.reg` + `drive_c` +
    `c:`）；
  - 游戏启动时的自动初始化、`--init`、`--fix-prefix` 三条路径同源收敛；
  - **已损坏前缀自动救**：有 `system.reg` 但缺 `drive_c`/`c:`（本 bug 的
    现场残留）也会被检出并备份重建。
- **[B2] Z 盘新指向**：`z:` → `/data/data/com.linbox/files/usr`（Z: 覆盖
  整个 Termux 前缀，对齐 Mobox `z:=files` 语义）。旧指向 `/` 自动迁移
  （一次性提示）；用户自设的其它有效目标保留不动；`DRIVE_Z` 环境变量/
  conf 可改（`DRIVE_Z=/` 恢复 wine 标准根文件系统）。
- **[B3] CWD 盘符映射守卫**：wine 把 Unix 工作目录映射为 Windows CWD，
  未映射时回退 `C:\windows` 并刷 `could not find DOS drive ...` 警告（游戏
  相对路径资源/CD 检测跟着丢）。z: 改指 usr 后终端默认目录 `$HOME` 恰在
  z: 之外 —— 守卫在启动前检查 `$PWD` 是否落在任一盘符下，未映射时自动
  切换到游戏目录（可映射）或 `$APP_PREFIX`（z: 根）。
- **[K1] zink 渲染（OpenGL on Vulkan）**：新增 `-z/--zink` 选项与
  `GLR_ZINK=1` 环境变量。mesa zink 缺件时自动补装（离线资产
  `opt/mesa/mesa-zink.tar.gz` 优先，否则 `pkg install mesa-glibc
  vulkan-icd-loader-glibc mesa-vulkan-icd-freedreno-glibc`，一次记账；
  `GLR_NO_GRAPHICS_SETUP=1` 逃生门），并导出
  `MESA_LOADER_DRIVER_OVERRIDE=zink` / `GALLIUM_DRIVER=zink` /
  `__GLX_VENDOR_LIBRARY_NAME=mesa` / `LIBGL_DRIVERS_PATH` + Turnip ICD
  （`VK_DRIVER_FILES`/`VK_ICD_FILENAMES` 指向检测到的
  `share/vulkan/icd.d/*freedreno*.json`）。
- **[K2] zink 诊断**：启动横幅 `gl` 行（`zink (ICD: freedreno_icd.aarch64.json)`
  / `无 Turnip ICD: 无硬件加速` / `zink 不可用`）；`-i` 信息输出 dri 驱动
  与 ICD 状态。

链路说明：termux-glibc 源的 `mesa-glibc`（24.2.6）自带
`glibc/lib/dri/zink_dri.so`；`mesa-vulkan-icd-freedreno-glibc` 即 Turnip
ICD（Adreno GPU 专用，debfix 会把 ICD json 里的 `com.termux` 路径等长改写
为 `com.linbox`）。渲染链：wine opengl32 →（box64 dlopen）→ libGL（GLVND）
→ mesa zink → libvulkan → Turnip → Adreno。

## 十六、v2.23.0 fix28：proton 收缩级联根治（-d/-f 通用，X11FitClient 决策环）

### 16.1 问题与根因（用户深采样 logcat 铁证）

用户实测矩阵：**wine-9.2 的 `-d`/`-f` 都能铺满；proton 的 `-d`/`-f` 都右/下黑边**。两份深采样 logcat（`logcat -d -t 20000 | grep -E "X11ResolutionLink|X11FitClient|..."`）给出的完整决策链：

| 时间线（-d 会话） | 事件 |
|------|------|
| 10:35:49 | 握手生效：`X 屏幕分辨率 → exact 1280x720（来自 glibc-runner）`，root=1280x720 |
| 10:35:53~58 | fit 线程等待 → 发现游戏窗口 **1232x693@(28,23)**（root 的 ~96.25%，恰 ×0.9625；proton 全屏管理器自己算出来的窗口） |
| 10:35:58 | 旧贴合策略：`窗口≠X屏 → applyFit(1232x693)` → **X 屏被缩** |
| 10:35:59 | proton 对 root 变化做反应：窗口重设为 **1220x678@(34,0)**（再次 ~96%）→ fit 又缩：`applyFit(1220x678)` |
| （-f 会话同型） | 级联共 3 轮：1232x693 → 1186x667 → 1129x634，画面越缩越小、四周黑边 |

**收缩级联闭环**：fit 缩 X 屏 → proton 全屏管理器把窗口重设为新 root 的 ~96% → fit 见"窗口≠X 屏"再缩 → …… wine-9.2 对 root 变化**无此反应**（窗口不动），贴合一次即收敛 —— 这就是两种 wine 表现迥异的根源。显示层拉伸（displayStretch）只能把"整张 X 屏"铺满 Android 窗口，root **内部**的黑边（游戏窗口小于 root 露出的四周）必须在 X 层解决。

### 16.2 fix28 新决策策略（X11FitClient，握手协议/-d/-f/-F 语义零变化）

| 机制 | 规则 | 作用 |
|------|------|------|
| ① 稳定门 | 窗口尺寸**连续两轮**观测一致（≈1.6s）才允许动 X 屏 | 绝不追着正在变化的窗口缩 root（级联引爆点） |
| ② 缩屏预算 | 每次握手（`X11ResolutionLink.apply` → `resetSession`）applyFit 至多 **2 次** | 级联在预算层面结构性不可能；开窗器→游戏两段式窗口刚好用完 |
| ③ 对抗窗+钉满 | applyFit 后 **4s** 内窗口再度缩水 = proton 对抗 → "钉满"：把游戏窗口撑回**覆盖整个 X 屏**（moveResizeWindow，root 不动），游戏/DXVK 收 WM_SIZE 按屏幕分辨率重绘 | proton 场景收敛路径：一次贴合 + 一次钉满 → 全屏铺满；稳定但预算耗尽/异常小窗同样钉满兜底 |
